كلمه inter process communication جايه اصلا من ال operating systems و ازاي ال processes بتتفاعل مع بعض. بس الموضوع داخل فيه تفاصيل كتير زي ازاي هيحصل information and resource sharing. لو عايز تقرا شويه عن الموضوع من ناحيه ال computer science ممكن تبص علي ال wiki دا https://en.wikipedia.org/wiki/Inter-process_communication 
خلينا نتكلم شويه ازاي الكلام دا ممكن يتطبق برضه بعيدا عن ال operating systems و احنا بن develope applications. ودا اللي هبقي مركز عليه في ال blog دي لأن الكلام عن ال IPC من وجه نظر ال application development هيكون مختلف شويه و بيستخدم طرق مختلفه عن اللي بيحصل في ال operating systems.
في معلومه عايز اصححها قبل ما ابدأ كلام و هيا ان ال IPC مش حكر علي ال microservices ولا علي ال backend development ولكن ال IPC بتدخل في تفاصيل اي اتنين components بيكلمو بعض

* Mobile/web to servers (via web APIs)
* IoT devices and sensors
* Services to services
* Modules to other modules
* Systems/services to databases or cache redis servers

ف بشوف ان اي حد بيكتب اي نوع من انواع ال software هيكون مهم جدا انه يعرف عن ال [IPC](https://en.wikipedia.org/wiki/Inter-process_communication).
خلينا نحاول نبسط الموضوع شويه. اي project/product بنعمله ما هو إلا مجموعه من ال features/usecases اللي بتقدم خدمه معينه. عشان ننفذ اي feature دا هيطلب ان شويه processes/components انها ت communicate مع بعض. مثلا اي system/service بنعملها هيا في الغالب دايما هتحتاح تتكلم او ت communicate مع service تانيه عشان تنفذ شغلها. علي سبيل المثال هتحتاج تتكلم مع service تانيه او علي الاقل هتحتاج تتعامل مع database او storage system او حتي تتكلم مع service تانيه.
ف نبدا كلامنا الاول بالكلام علي انواع ال communication ما بين ال systems (او ما يسمي بال inter process communication) و ايه هيا طرق تنفيذهم

## Pipes

هنا بيكون الاتصال بيبدا من طرف و يوصل لطرف تاني. و بيكون في اتجاه واحد فقط. مش في اتجاهين. ممن نبسطها اكتر و نقول ان في طرف هيكون بيكتب و طرف تاني هيكون بيقرا.

ال pipes كمان هيا حاجه مدعومه من معظم نظم التشغيل و لفات البرمجه.
خلينا مثلا نشوف مثال بسيط من golang

```golang
package main

import (
	"fmt"
	"io"
	"os"
	"os/exec"
)

func main() {
	// Create a pipe
	reader, writer, err := os.Pipe()
	if err != nil {
		fmt.Fprintf(os.Stderr, "pipe: %v\n", err)
		os.Exit(1)
	}

	// Start a child process
	cmd := exec.Command(os.Args[0], "child")
	cmd.Stdin = reader // Connect pipe's read end to child's stdin
	cmd.Stdout = os.Stdout
	if err := cmd.Start(); err != nil {
		fmt.Fprintf(os.Stderr, "start: %v\n", err)
		os.Exit(1)
	}

	// Check if running as child (reader)
	if len(os.Args) > 1 && os.Args[1] == "child" {
		// Child process: read from pipe (stdin)
		data, err := io.ReadAll(os.Stdin)
		if err != nil {
			fmt.Fprintf(os.Stderr, "read failed with error: %v\n", err)
			os.Exit(1)
		}
		// Child (reader) prints the message
		fmt.Printf("Reader (child) received: %s\n", data)
		os.Exit(0)
	}

	// Parent process: write to pipe
	msg := "Hello from parent!"
	_, err = writer.Write([]byte(msg))
	if err != nil {
		fmt.Fprintf(os.Stderr, "write failed with error: %v\n", err)
		os.Exit(1)
	}
	writer.Close() // Close write end to signal EOF

	// Wait for child to finish
	if err := cmd.Wait(); err != nil {
		fmt.Fprintf(os.Stderr, "wait failed with error: %v\n", err)
		os.Exit(1)
	}
}
```

في المثال دا هتلاقي اننا بدأنا child process و فضلت مستنيه انها تستلم اي رساله. و زي مانت شايف كدا هيا بتستقبل بس مش بتقدر تبعت.
و بعدين هتلاقي اننا خلينا ال parent processing تكتب رساله و تبعتها لل reader

طيب ازاي المسج وصلت من ال writer to the reader?
بص علي اول سطر في البرنامج هتلاقي ان ال pipe هوا اللي قال مين ال reader و مين ال writer

طيب هل ينفع نستخدم ال pipes في ال http communication?
لأ طبعا لأن ال http communiation is bidirectional not unidirectional
يعني اللي بيبعت request بيقدر برضه يقرا ال response

## Shared memory

في النوع دا بيكون في مكان معين في الذاكره يقدر اكتر من proccess انهم يقروا و يكتبو في نفس المكان. و النوع دا من ال communication سريع جدا. و لكن زي ما انت بتفكر دلوقتي الطريقه دي لازم ناخد بالنا مين بيقرا ايه و امتي. و دا اللي هنتكلم عنه كمان شويه.

المهم خلينا نشرح اكتر ال shared memory بيشتغل ازاي
الاول بنحدد المكان اللي عايزين نكتب و نقرا منه. و دا بنعمله باني بقول لنظام التشغيل اديني مكان في الذاكره حجمه كذا. و هوا هيرد عليك. في غالبيه لغات البرمجه بيكون في function اسمها shmget ودي موجوده مثلا في C lang and Go lang
بعدها بنقوله اديني بقي عنوان ال segment دي عشان اقدر اكتب و اقرا منها. في غالبيه اللغات هتلاقي في function اسمها shmat بترجع العنوان دا
بعدها تقدر تكتب علي العنوان دا.
و اي process تاني تقدر ت attach نفسها للعنوان دا و تكتب و تقرا منه برضه

خلينا نشوف مثال علي كدا

```golang
package main

import (
    "fmt"
    "golang.org/x/sys/unix"
    "log"
    "unsafe"
)

const (
    // IPC_PRIVATE is used to create a private shared memory segment
    ipcPrivate = 0
    // Permissions: 0666 (read/write for owner, group, others)
    shmPerm = 0666
    // Size of shared memory (4 bytes for an int32)
    shmSize = 4
)

func main() {
    // Create shared memory segment
    shmid, err := unix.SysvShmGet(ipcPrivate, shmSize, unix.IPC_CREAT|shmPerm)
    if err != nil {
        log.Fatalf("shmget: %v", err)
    }
    defer func() {
        // Remove shared memory segment
        if err := unix.Shmctl(shmid, unix.IPC_RMID, nil); err != nil {
            log.Printf("shmctl IPC_RMID: %v", err)
        }
    }()

    // Attach to shared memory segment
    shmaddr, err := unix.ShmAt(shmid, 0, 0)
    if err != nil {
        log.Fatalf("shmat: %v", err)
    }

    // Write to shared memory (store 42 as int32)
    sharedData := (*int32)(unsafe.Pointer(&shmaddr[0]))
    *sharedData = 42

    // Detach from shared memory
    if err := unix.ShmDt(shmaddr); err != nil {
        log.Fatalf("shmdt: %v", err)
    }

    // Reattach to shared memory
    shmaddr, err = unix.ShmAt(shmid, 0, 0)
    if err != nil {
        log.Fatalf("shmat (reattach): %v", err)
    }
    defer func() {
        // Detach from shared memory
        if err := unix.ShmDt(shmaddr); err != nil {
            log.Printf("shmdt: %v", err)
        }
    }()

    // Read from shared memory
    sharedData = (*int32)(unsafe.Pointer(&shmaddr[0]))
    fmt.Printf("Shared data: %d\n", *sharedData)
}
```


## Semaphores and mutexes

زي ما حكينا فوق لو عندي shared memory ف دا بيخلي اي حد يقدر يكتب في اي وقت و اي حد يقدر يقرا في اي وقت. ودا بيعمل مشكله مشهوره اسمها race condition.
طب الاول يعني ايه race condition?
تخيل ان عندك اتنين طباخين بيعملو كيكه. و الاتنين شغالين في نفس الوعاء. لازم نتاكد مثلا اننا حطينا البيض قبل الزبده و ان مش الاتنين حطو زبده وإلا الطبخه تبوظ. و دا نفس الكلام في ال shared memory.
دا ببساطه يعني ايه race condition

ال semaphores and mutexes دي طرق بنستخدمها عشان نعمل coordination عشان ميحصلش race condition.

خلينا ندي مثال علي ال semaphore
تخيل عندك مكان لركن العربيات بس تقدر تركنه فيه ٣ عربيات بس. و في سايس علي باب الجراج. اهو السايس دا هوا ال semaphore.
بيشوف لو في مكان محدش بيستخدمه ف بيعديك او كل ما الاماكن كلها تتملي بيقفل الباب عشان محدش يدخل.
و علي فكرا اول ناس اخترعت النظام دا هوا نظام القطارات عشان القطارات و هيا بتغير طريقها متصطدمش ببعض.
